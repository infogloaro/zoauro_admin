## Summary
Three read-only, scope-aware aggregate endpoints with no schema change. Each is cached in Redis for 60 s under a key holding the scope hash and the definitions, and each is built from the order-overview SQL pattern.

1) GET /customers/summary (customers:view) feeds a KPI row on the Customers list. It returns registered customers (D25-visible), new this period, buying customers, returning customers (and %), lifetime spend, AOV and satisfaction. Satisfaction is the average published review rating and is null when there are no reviews. Money figures count only zones where the member also holds payments:view, following D182 O2.

2) GET /delivery-partners/performance?partnerId=... (delivery:view) feeds a totals row on the partner list and a "Last 30 days" column for the visible page. It returns orders delivered, on-time %, average delivery minutes (assignment to delivered) and failed deliveries (cancelled while a partner was assigned).

3) GET /delivery-partners/{id}/performance feeds a Performance card on the partner record, with the latest late or failed orders.

Every business number comes from one new Control Panel setting, `kpi.definitions`, under the D190 standing rule. It is in group 'orders' and platform-wide, with defaults: period 30d, returning = 2 or more delivered orders, on time = delivered within 40 min of assignment, pre-order grace 10 min. Periods reuse the dashboard IST ranges.

An idempotent demo seed step adds reviews, about 10% late deliveries and a few failed deliveries, so the figures are not flat 100% / 0 / "—" on stage.


## New decisions (team defaults, D190 standing rule)
- Customer KPI definitions (doc 62 idea; the owner said 'owner to define', so these are D190 team defaults the Super Admin can change) — **default:** All figures cover the effective scope and the selected period (IST window from dashboardWindow). registered = customers visible under D25, not deleted, all-time. newInPeriod = visible customers with created_at in the window. buyers = distinct customers with at least one DELIVERED order placed in the window. returning = buyers who have returningMinOrders (default 2) or more DELIVERED orders in scope, lifetime. returningPct = returning/buyers (1 decimal, null when there are no buyers). lifetimeSpendPaise = sum(total) of DELIVERED orders, all-time. aovPaise = round(sum(total)/count) of DELIVERED orders placed in the window (null when 0). satisfaction = avg(rating) of reviews with status PUBLISHED, not deleted, on in-scope orders placed in the window, any target; null when there are 0 reviews. The KPI row ignores search/tab/source and follows only the zone switcher.. _Why:_ The brief lists the figures but doc 62 leaves the definitions to the owner. D190 says the team's proposal is the default until the Super Admin changes it, so record it as a new D row (next free number after D192) and in doc 32.
- Partner performance definitions — **default:** Window by delivered_at for deliveries and by cancelled_at for failures. delivered = orders DELIVERED by the partner in the window. Delivery minutes = delivered_at minus the latest ASSIGNED history row (fallback ready_at, then placed_at). On time: an order-now is on time when delivery minutes <= onTimeMinutes (default 40); a pre-order is on time when delivered_at <= scheduled_for + preorderGraceMinutes (default 10). onTimePct to 1 decimal, null when there are 0 deliveries. avgDeliveryMinutes is the mean of delivery minutes to 1 decimal. failed = orders CANCELLED while delivery_partner_id = the partner. An unassign (ASSIGNED->READY) is NOT counted, because it clears the partner id; that waits for post-demo.. _Why:_ No promised time or assigned_at column exists, and there is no FAILED status. The assignment-to-delivered leg is the part the partner controls. These need a D row and doc 32.
- New Control Panel setting kpi.definitions (D190: business numbers are settings) — **default:** key 'kpi.definitions', group 'orders' (area settings.orders, so no new D178 area), label 'Customer and delivery partner figures'. Schema {defaultRange: enum DASHBOARD_RANGES = '30d', returningMinOrders: int 2..50 = 2, onTimeMinutes: int 5..240 = 40, preorderGraceMinutes: int 0..120 = 10}. zoneOverride false, reauth PASSWORD, editable true, appsRead false, effect ENFORCED.. _Why:_ Platform-wide (no zone override) keeps multi-zone totals coherent: one threshold per aggregate. A per-zone threshold would need per-order zone joins and can follow after the demo. orders.sla is not reused because its stage targets flag live delays and its defaults (40 min out-for-delivery alone, 55 min assignment to delivered) are a different promise.
- Money KPIs need payments:view as well as customers:view — **default:** lifetimeSpendPaise and aovPaise are computed over zonesFor(customers:view) ∩ zonesFor(payments:view). The money block is null when that set is empty. partial=true when the set is smaller than the KPI scope, and the UI then shows 'Counts <zones> only'. The per-row totalSpentPaise in GET /customers stays as today (D25).. _Why:_ This mirrors D182 O2 (GMV/AOV only with payments:view) on a new aggregate screen. Karthik (Operations in CBN) must not see CBN money. It needs a one-line D row or doc 04 note.
- Three new read endpoints (doc 09 rows) — **default:** GET /customers/summary (customers:view, zone: query). GET /delivery-partners/performance (delivery:view, zone: query, partnerId repeatable, at most 50). GET /delivery-partners/{id}/performance (delivery:view, zone: none; 404 outside view scope). No new permissions: the existing customers:view, delivery:view, payments:view and orders:view keys are reused.. _Why:_ AGENTS.md: no invented endpoints without the doc 09 rows. Keeping them separate keeps the existing lists fast and lets each be cached on its own.
- Requested zone where the module is not viewable (Zonal Admin assigned to the zone but without customers:view / delivery:view there) — **default:** Same as GET /customers and GET /delivery-partners today: zero/null figures, no 404. An unassigned zone is still 404 ZONE_NOT_FOUND (access-service). With the module viewable nowhere, the route guard returns 403.. _Why:_ Consistent with the existing list behaviour, so the list and the KPI row never disagree. Calling it out because AGENTS.md mentions 404 for an unviewable module on read.
- Cache TTL and key — **default:** Redis 60 s (doc 23 allows 30-60 s). Key 'kpi:v1:<route>:<range>:<SA|ZA>:<sha256(sorted scope ids | sorted money ids | sorted partnerIds | JSON of definitions)>'. A Redis failure falls back to computing the value. Not invalidated on writes; a settings change shows up within 30 s because the definitions are part of the key.. _Why:_ Same rule as the dashboard (TC-MZ-6: no cache shared across scopes).

## Demo seed
New idempotent step apps/api/scripts/demo/performance.ts, called from seed.ts after orders and before finance. On an already-seeded zoauro_demo it can run alone (a probe flag), so the 30-day history does not need rebuilding. Running it writes to the demo database, so get the owner's explicit approval first. It uses the deterministic mulberry32 PRNG:
(a) Late deliveries. For about 10% of DELIVERED history orders older than today, chosen by an orderNo hash, push delivered_at and the DELIVERED order_status_history.created_at 20-35 min later, only when the new time stays on the same IST day (payouts and COD week buckets are unchanged). This gives on-time around 85-92% per partner.
(b) Failed deliveries. Insert about 6 orders over the last 30 days across CBE/CBN/TUP: COD, payment PENDING, timeline PLACED->...->OUT_FOR_DELIVERY->CANCELLED, delivery_partner_id set, cancel_reason 'Customer not reachable'. No money moves, deliveries_count is unchanged, and cash_in_hand is untouched.
(c) Reviews. For about 45% of DELIVERED history orders, add one DELIVERY review (target = the partner, rating 3-5, weighted to 4-5) and for about 30% one RESTAURANT review (target = the vendor), status PUBLISHED, created_at = delivered_at + 1-6 h. Then recompute delivery_partners.rating_avg from the DELIVERY reviews, so the record's Rating matches.
Marker for idempotency: skip when any review with a comment starting 'demo:' exists. It logs counts. Insert in chunks of 40 inside transactions (low RAM, as orders.ts does). Also add the new act to docs/F-execution/61_Demo_Script.md.

## Performance
Aggregates only: no row lists are loaded into Node. Each endpoint runs 2-4 $queryRaw/groupBy statements in parallel with bound parameters (Prisma.sql / Prisma.join, no concatenation), the same as overview.repository.ts. Index use: zone+status+placed_at for period scans (partner totals add placed_at >= from - 8 days so the composite index applies), (delivery_partner_id,status) for the at most 50 page partners, (customer_id) for returning, history (order_id,created_at) through LATERAL for the ASSIGNED time, reviews (order_id). Redis cache for 60 s keyed by route+range+role+sha256(scope ids, money ids, partner ids, definitions); a Redis outage falls back to computing. SettingsReader is cached in process for 30 s. Web: the KPI queries are separate from the list query, so the table never waits for figures. staleTime 30 s, keepPreviousData on range/zone change, skeleton StatCards. Partner page performance runs one request for the visible 25 ids, enabled after the list arrives. Targets: under 300 ms on the demo DB, p95 under 2 s at 100k orders (doc 25 gate). Optional post-demo indexes are listed under schemaChanges.
