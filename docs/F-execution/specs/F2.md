## Summary
Bring Delivery Partner Requests (R12) level with the D170 vendor onboarding queue, and keep it as its own page.

Stored data: delivery_partners gets the existing OnboardingStage enum (onboarding_stage, onboarding_stage_at) through a NEW migration with a backfill.

Backend: the delivery-partners module gains three routes, all following the onboarding module's pattern:
- GET /delivery-partners/onboarding: the queue, oldest in stage first, with stage, age and Needs-a-zone counts, a documents-checked count and the last more-info message.
- POST /delivery-partners/{id}/onboarding/review: claims the record (D174), then SUBMITTED or MORE_INFO_REQUIRED goes to UNDER_REVIEW.
- POST /delivery-partners/{id}/onboarding/more-info: UNDER_REVIEW goes to MORE_INFO_REQUIRED ("Waiting for partner"). The message reaches the partner app through a new outbox event, partner.more_info_required.

The existing verification route also sets the stage to DECIDED in the same transaction. Age levels come from the existing Control Panel setting onboarding.ageWarnings (24 h / 48 h); no new setting.

Web: a new PartnerRequestsPage, copied from OnboardingPage, replaces PartnersPage mode="requests" on both role routes:
- Super Admin tabs All / Needs a zone.
- Stage chips (Open, Submitted, Under review, Waiting for partner, Decided) and age chips, each with counts.
- Columns Applicant + vehicle, Zone (only when more than one zone is in scope), Area, Stage + reviewer claim badge + asked message, In this stage, Docs n/m, Actions.
- Actions: Start review, then Decide (opens the partner page where Verify/Reject already live), or Ask for more info.

The partner detail page shows the stage badge. Demo seed puts the four app sign-ups in every stage and age, through the real routes.

Authorization:
- Reads: zonesFor(ctx,'delivery:view').
- Writes: delivery:status in the partner's zone (403), plus delivery:edit for the claim.
- A partner outside view scope gives 404, an unassigned ?zoneId gives 404 ZONE_NOT_FOUND, and an unzoned record gives 409 CONFLICT until a Super Admin moves it into a zone.

This closes the 2026-10-21 audit gap "partner onboarding review/more-info routes" (handoff.md:610).


## New decisions (team defaults, D190 standing rule)
- Should partners join the unified Vendor Onboarding queue (GET /onboarding) or keep their own Delivery Partner Requests page? — **default:** Keep the separate R12 page and nav entry 'partner-requests', but use the same layout, stages, age chips and actions as Vendor Onboarding. The backend lives in the delivery-partners module, with the same route shape as D170: /delivery-partners/onboarding, /delivery-partners/{id}/onboarding/review and /more-info. ONBOARDING_MODULES and OnboardingItem stay unchanged. Record this as D199 (next free number; D198 is the highest in doc 03).. _Why:_ D170 defines the vendor queue by vendor types. GET /onboarding is guarded by restaurants:view and OnboardingItem.status is a VendorStatus. Partners use the separate 'delivery' permission module and PartnerStatus, and D132 and nav entry R12 already give them their own page. Doc 60 §4.3 and the doc 60 HTML ("Same layout as vendor onboarding, with partner documents") also describe two pages. Mixing them would widen the vendor queue's permission guard and touch onboarding/*.ts, which lane B2 is editing today.
- Is 'request more information' for a partner a REJECTED decision with a note (D132 today), or a MORE_INFO_REQUIRED stage like vendors (D170)? — **default:** Use the MORE_INFO_REQUIRED stage: verification_status stays PENDING and the row shows 'Waiting for partner' with the message. Reject (note required) stays as it is and is a real rejection. This supersedes only the 'request more information = REJECTED with a note' clause of D132; record that in D199 and doc 32.. _Why:_ The brief asks for parity with D170. Today a rejection used as a request reads as Rejected to the partner app and in the Rejected count.
- Which outbound event carries the more-info message to the partner app? — **default:** A new event type partner.more_info_required to PARTNER_APP. data: {stage:'MORE_INFO_REQUIRED', message}; audience: {partnerId, zoneId}; aggregate: {type:'partner', id, version}. Add it to contracts/events.catalog.json, apps/api/src/lib/outbox/catalogue.ts and doc 43 §outbound before any code.. _Why:_ lib/outbox/catalogue.ts routes by event type to app client types. Adding PARTNER_APP to onboarding.more_info_required would also send vendor messages to the partner app. AGENTS.md: change the contract first.
- Should DECIDED be stored or derived for partners? — **default:** Store it. verify() sets onboardingStage='DECIDED' and onboardingStageAt=now in the same transaction. The migration backfills DECIDED where verification_status <> 'PENDING', and stage_at = COALESCE(verified_at, created_at). Queries still treat verificationStatus <> 'PENDING' as DECIDED, defensively.. _Why:_ The partner module owns its verification route, so storing the stage keeps the list a plain indexed Prisma query, (zone_id, onboarding_stage, onboarding_stage_at), instead of the CASE-in-UNION the vendor queue needs.
- Age thresholds for partner requests — **default:** Reuse the existing setting onboarding.ageWarnings (default 24 h warn / 48 h late, not zone-overridable). Read it through settings.reader.onboardingAgeWarnings(), injected as deps.ageWarnings, the same as lane B2 does for vendors. No new key. Lane B1 or B2 adds 'and Delivery Partner Requests' to the registry description and effect text, because B1 owns registry.ts today.. _Why:_ D190 standing rule: every business number is a Control Panel setting with a default. The owner described one age rule for onboarding (D170).
- Which permissions do Start review and Ask for more info need? — **default:** The route needs requirePermission('delivery','status') and the service needs assertCanWrite('delivery:status', zone). Start review also needs delivery:edit, because claims.claim() checks it. The web canAct flag is true when a zone has both delivery:status and delivery:edit. If W7's fix for vendors decides differently (status only), follow W7 for partners as well.. _Why:_ This matches the vendor routes (restaurants:status plus the claim's :edit). W7 is fixing the onboarding canAct mismatch today, so both pages should end up with the same rule.
- Should review and more-info take an If-Match version? — **default:** No If-Match, the same as the D170 vendor routes. The transaction takes the row lock (FOR UPDATE), rechecks the stage (409 INVALID_STATE_TRANSITION 'moved on; reload') and bumps the version through repo.set(), so app receivers order events correctly.. _Why:_ Parity with the shipped onboarding routes and the web OnboardingPage pattern. The stage recheck under the lock gives the same protection against two admins acting at once.
- Partner resubmission after a more-info request (MORE_INFO_REQUIRED back to SUBMITTED) — **default:** Not built in F2: there is no partner update intake (only POST /intake/partners create). An admin can Start review again from MORE_INFO_REQUIRED, as on the vendor queue. Log it in doc 32 as post-demo, for the intake contract.. _Why:_ 'App intake beyond vendor applications' is on the known not-built list, and changing the intake contract is out of scope for the demo.
- Docs column on the queue — **default:** docs = {accepted, required}: the number of mandatory catalogue types (settings onboarding.documents, DELIVERY_PARTNER) whose newest vendor_documents row is verified, over the number of mandatory types. null when the catalogue is not configured.. _Why:_ Doc 60 HTML lists 'Docs' as a column. It reuses the D145 catalogue that PartnerDetail.checklist already reads.
