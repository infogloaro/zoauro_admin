## Summary
Add a read-only `onboarding` block to GET /restaurants/{id}, /homemakers/{id} and /hotels/{id}, and to every write that returns that detail. The block holds the stage, the time it entered that stage, ageHours, ageLevel from the onboarding.ageWarnings setting, the latest more-info request, and a short history: Submitted, Review started, More info requested, Verified, Rejected.

Where the data comes from:
- The record row: onboarding_stage, onboarding_stage_at, verification and created_at. DECIDED is derived the same way as the queue's STAGE SQL.
- One indexed audit_logs read per detail, limited to the four onboarding actions of that entity, newest 20.

No new endpoint, table, enum, permission or migration. The more-info and review routes already exist and are reused unchanged.

On the web, a new OnboardingStageCard sits under the ClaimBanner on VendorDetailPage and HotelDetailPage. It shows:
- the stage badge, an age badge (24 h / 48 h colours) and "Waiting for vendor: <message>",
- the history as an ordered list,
- buttons: "Ask for more info" when the stage is UNDER_REVIEW, and "Start review" when it is SUBMITTED or MORE_INFO_REQUIRED (proposed default; same existing route as the queue).

The queue's MoreInfoDialog moves to its own file and both screens use it. Buttons show only when the member holds `<module>:status` in the record's zone; the API stays the authority. After an action, the record, the queue and the claims queries reload.

Build after the lanes commit B2 (onboarding/server.ts), W5/W6 (VendorDetailPage) and W7 (OnboardingPage / onboarding-page-props). These files are being edited now.


## New decisions (team defaults, D190 standing rule)
- Shape of the new detail field: a flat onboardingStage (brief wording) or a nested `onboarding` object — **default:** Nested `onboarding: { stage, stageAt, ageHours, ageLevel, lastMoreInfo: {message, at, by} | null, history: [{kind, at, by, note}] }` on restaurantDetailSchema, homemakerDetailSchema (via vendorDetailBase) and hotelDetailSchema; one schema `recordOnboardingSchema` in packages/shared/src/onboarding. _Why:_ One object is reused by three detail DTOs and the stage card; the fields match onboardingItemSchema names (stage, stageAt, ageHours, ageLevel), so screens and tests use one vocabulary. Needs a doc 09 note and a doc 32 row (new response field).
- Source of the record history — **default:** The audit_logs rows of `<entity>.onboarding_review_started`, `.more_info_requested`, `.verified` and `.rejected` for the entity (index entityType+entityId+id desc, newest 20, shown oldest first), plus a first SUBMITTED entry made from the record's created_at. `by` = actor_name when actor_type is ADMIN, otherwise null; `note` only for MORE_INFO_REQUESTED (the message) and REJECTED (the reason). _Why:_ No new table or migration during the demo freeze. The onboarding repository already reads more-info notes from audit_logs. Admin names and the rejection note are already visible on the record (verifiedBy, verificationNote, ClaimBanner).
- Also offer 'Start review' on the record page (the brief only asks for Ask for more info) — **default:** Yes: 'Start review' when the stage is SUBMITTED or MORE_INFO_REQUIRED, 'Ask for more info' when it is UNDER_REVIEW, nothing when DECIDED or when there is no zone. Both use the existing routes. _Why:_ Without it, a Submitted or Waiting-for-vendor record has no action on its own page. Vendor resubmission through intake is not built, so Start review is the only way out of MORE_INFO_REQUIRED, and it makes the demo repeatable.
- Which members see the action buttons — **default:** Super Admin, or a Zonal Admin who holds `<module>:status` in the record's own zone. Add `statusZoneIds: string[]` to VendorPageProps and HotelPageProps (from /me) and check `v.zone.id`. The API still answers 403/404. _Why:_ can.status today means 'somewhere', so Admin(A+B) with read-only B would get a button that returns 403 on a B record. The owner asked for no errors in the demo. Web-only convenience, no contract change.
- Concurrency of more-info and review (no If-Match on these routes) — **default:** Keep as built: FOR UPDATE lock plus the stage re-check gives 409 INVALID_STATE_TRANSITION. The record page shows the message and refetches the detail. No contract change before the demo; note it in doc 32. _Why:_ AGENTS asks for If-Match on state changes, but these routes shipped without it and the onboarding stage is not the order state machine. Adding a version column needs a migration and changes the contract during the freeze.
- Seeded history timestamps — **default:** Accept that seeded 'Review started' and 'More info requested' entries carry the seed-run time, while stageAt and createdAt are aged by the seed. The presenter talks about the stage age, not the history times. _Why:_ audit_logs is append-only (audit_logs_guard trigger), so the seed cannot backdate the rows, and inserting fake audit rows is not acceptable.

## Risks
1. Hot files: VendorDetailPage.tsx (W4/W5/W6), OnboardingPage.tsx and onboarding-page-props.ts (W7), onboarding.service.ts / onboarding.repository.ts / server.ts (B2), and the generated openapi.json and api-client schema.ts (every lane) are being edited now. Build after those commits land. Use the .git/zo-commit.lock protocol and stage only F1 hunks. New logic goes in new files (onboarding.record.ts, MoreInfoDialog.tsx, record-actions.ts, OnboardingStageCard.tsx) to keep the edits to shared files small.
2. A new required field on three shared detail schemas means every code path that builds a Detail must fill it, which is why it is split by module (B-F1.2 vendors, B-F1.3 hotels). VendorsService.toDetail casts with `as`, so a missing field there would not fail typecheck. The integration test must parse responses with the shared schemas to catch it.
3. Vendor resubmission through intake (MORE_INFO_REQUIRED back to SUBMITTED) is not built. A record stays 'Waiting for vendor' until an admin presses Start review; the card copy must not promise the app resubmits.
4. Seeded history times are the seed-run time while the stage age is backdated (audit_logs is append-only). The presenter should talk about stage age, not history timestamps.
5. A live claim by another admin gives 409 RECORD_CLAIMED. Re-running the seed less than 30 min before the demo leaves Karthik's and Suresh's claims live, so Arun would get the claimer message (handled, but avoid it on stage).
6. The more-info and review routes have no If-Match. Two admins acting at once get 409 INVALID_STATE_TRANSITION, which the card handles by refetching. Recorded in doc 32 instead of adding a version column during the freeze.
7. Hotels have no `source` column and no documents step (doc 61), so the hotel SUBMITTED entry reads 'Added' / 'Submitted' without the app wording.
8. Low-RAM laptop: run the DB integration tests under .git/zo-dbtest.lock, one lane at a time, and run only the onboarding, vendors and hotels test files while iterating.
